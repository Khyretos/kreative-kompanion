# KG-02: hierarchical planner

- `server/src/planner.rs`: plan types, JSON schema for the model (response_format), parse, sizing rules (default 5 files, 250 lines per task; paths counted once), checks (duplicate keys, unknown/self deps, dependency loops, missing done-when, empty milestones), `generate` (up to 3 rounds, each broken rule is sent back to the model), `apply` (goal > milestones > tasks + deps in one transaction, refuses an invalid plan), `apply_replan` (new tasks as subtasks of the failed task, inheriting its deps), proposals table (migration 0123).
- `server/src/planner_web.rs`: POST /api/projects/{id}/plan, GET /api/projects/{id}/plans, POST /api/plans/{id}/apply|dismiss, POST /api/tasks/{id}/replan. A task that ends in needs_input (not stopped by the user) gets a re-plan proposal automatically; nothing enters the tree until applied.
- Uses the user's orchestrator role. A provider without response_format support falls back to a plain answer; parser and checks still apply.
- No UI yet: the proposals are API-only (a later task can show them on the Plan tree).
