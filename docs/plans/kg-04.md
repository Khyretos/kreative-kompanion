# KG-04: escalation ladder

## Change

- `[[ladder]]` in kompanion.toml (name, provider, model, optional fix_rounds): rungs a task run escalates to.
  Rung 0 is the worker role as assigned; none configured means the old behaviour (ask the user at once).
  A strong model on any provider is opt-in: it only runs when added there.
- `server/src/taskrun/mod.rs`: `run()` keeps the folder check, then loops over rungs. `attempt()` is the old
  plan, steps and review/fix loop; it returns `Outcome::Failed(why)` for what another model may fix (planning
  failed, no plan, a step stopped, the fix stopped, review failed after all fix rounds) and ends the run for
  good for what it cannot (stopped by the user, budget used up, folder missing, check could not run, a test the
  task may not change, the reviewer model failing). A rung replaces orchestrator and worker (the reviewer stays,
  so the judge is the same), is skipped when its provider is not configured or its model was already tried, and
  may cap fix rounds. KG-03 time and token budgets still cover the whole run.
- `taskrun/ladder.rs`: next rung, the per-rung log entry (`runs.ladder`, migration 0126: rung, name, model,
  why it ran, tokens, minutes, fix rounds, outcome; also in the run report as `ladder`), and the text the user
  gets after the last rung: one line per rung with what it tried.
- The task note and the project thread say each escalation ("X did not finish (why). Trying Y").

## Tests

`cargo test`: 459 pass (4 new: next rung skips tried models and missing providers; the user text lists every
rung; `[[ladder]]` parses; a rung takes over planning/work, keeps the reviewer and caps fix rounds). The
escalation loop itself needs a model and a paired computer: not exercised live (no second rung configured on
this Kompanion), so the loop is covered by code review only.
