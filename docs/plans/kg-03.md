# KG-03: task queue scheduler

- `server/src/scheduler.rs`: the rules (tested in `scheduler_tests.rs`) and the loop. Every 20 s each project with the scheduler on gets one round: queued tasks whose dependencies are all `done` (a failed or unknown dependency never lets a task start; a task with unfinished subtasks waits for them) go, in queue order, to free computers, one task per computer. A computer is free when its runner reported within 90 s, it runs no task, and the GPUs configured on it have no queued or running GPU job. A task without a check command (its own, else the project's) is not started: it goes to `needs_input` with the reason.
- Settings per project (`projects.scheduler`, migration 0124): `{enabled, machines: {computerId: folder}, check, budget}`. Off by default. API: `GET/PUT /api/projects/{id}/scheduler`, `POST /api/projects/{id}/scheduler/tick` (one round now), `PUT /api/tasks/{id}/budget`.
- Done only when the check passes: after the reviewer says ok, `taskrun` runs the check command as a shell job and reads its `exit:` line. Exit 0 passes. A non-zero exit becomes a review finding and a fix round. A check that cannot run (not granted, no exit code, timeout) leaves the task in `needs_input`, never `done`. This applies to hand-started runs with a check as well.
- Budgets for scheduled runs: minutes (default 60), tokens (400,000, summed over the run's model calls) and fix rounds (3, never above the effort's own). Task value, then project value, then default. A run over time or tokens stops at the next step or round with `needs_input` and the reason.
- Not done here: a UI for the settings (API only, like KG-02), and picking a computer by the task's GPU need beyond "no GPU job on it".
