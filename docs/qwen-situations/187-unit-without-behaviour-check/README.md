# Lesson 187: a unit without a behavioural check ships a spec violation

Situation: NOTIFY-TEST (2026-10-12), job `nt-send-test` (jobs.json): add `sendTest()` to web/src/core/desknotify.ts. The prompt said: when `Notification.permission` is not "granted", ask, and return a "blocked" result when the answer is not "granted". The unit's check was only `tsc` plus a grep for the function name (the behaviour tests need the Settings button, which is a later unit).
Wrong output: OVMS run 2 (accepted, it was the only OVMS pass; soucouyant passed 3 of 3 in 2 attempts each) tested only `Notification.permission === "denied"`, asked once and then sent the notification anyway unless the permission became something other than "denied" or "granted", so a denied permission still printed "Test notification sent." (wrong-browser-path.ts.txt). The last unit (`nt-main-action`) ran the 4 Playwright tests and the fourth, "a denied permission is explained", exposed it.
Corrected: corrected-browser-path.ts.txt (ask when not granted, block when the answer is not "granted"); Claude's fix, all 8 desknotify tests pass.
Lesson (Claude's mistake in planning the checks): give every unit a check that runs its behaviour. When a function's tests need later units, write a small test file for the function itself (the Playwright spec could have driven `sendTest` directly through a test hook) or run the unit with its tests once the last unit exists and fix forward at once. Also `nt-main-action` OVMS runs 1 and 2 changed nothing that made the tests pass (4/4 still failing); run 3 passed 3 of 4 and was used.
Rerun after model refinement: run jobs.json (nt-send-test) from a clean main with the 4 tests present and see whether the denied path is blocked.
