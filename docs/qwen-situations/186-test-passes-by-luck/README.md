# Lesson 186: a unit that passes its tests can still be wrong

Situation: job `gp-prefer` (M6-11, 2026-10-12): `prefer_library` swaps a generated asset for the library asset that shares the most tags, tags and kinds compared lower-cased. job.json is the job; runs/prefer-* the six runs (OVMS 0/3, soucouyant 1/3: run 3 passed first try and was accepted).
Wrong output: the accepted soucouyant draft did not lower-case the tags and, when comparing two candidates, intersected the best candidate's tags with the current candidate's tags instead of the task's (wrong-prefer-accepted.rs.txt). Claude's test `library_assets_are_preferred_over_generating` used the task tag "Knight" against library tag "knight"; without lower-casing a07 still won on the tag "run", so the draft passed by luck. The next unit's test (generate, `library_assets_are_swapped_in_before_the_checks`) exposed it: 3 of the 6 generate runs (OVMS r1, soucouyant r2 and r3) failed only on it although their own code was right; the other 3 had compile errors (runs/generate-*).
Corrected: corrected-prefer.rs.txt (lower-cased sets, best match tracked as (shared, asset)); Claude's fix, the 2 prefer tests and all 23 gameplan tests pass.
Lesson for the tests (Claude's mistake): a rule the model can ignore must make the test fail when ignored; "Knight" vs "knight" must have been the only overlap. Rerun after model refinement: run job.json and check whether the draft lower-cases and picks a12 in the generate test.
